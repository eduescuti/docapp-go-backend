Cómo funciona el backend

La app del celular no guarda los datos: le pide todo a un servidor (la API) por internet. El servidor revisa quién pide, aplica las reglas de negocio y lee o escribe la base de datos. Acá está, paso a paso y en simple.

Las capas

El código está en backend/src/, ordenado como la práctica de la cátedra (Express + Prisma). Cada capa hace una sola cosa.

🧭 Rutas · rutas/

Reciben el pedido HTTP, leen y validan el body y la URL, y llaman al servicio. No tienen reglas de negocio ni usan Prisma.

  • index.ts el mapa: un prefijo por router
  • auth.ts login, sesión y registro
  • turnos.ts, medicos.ts, admin.ts…

⚙️ Servicios · servicios/

El corazón: las reglas (cobertura, 24 h, franjas, quién ve qué). Están en carpetas por tema, las mismas que en la app, y usan transacciones cuando hay que cambiar varias cosas juntas.

  • turnos/ disponibilidad, estados y feedback
  • catalogos/cobertura.ts quién ve qué según su plan
  • sesion/ login, tokens y DNI escaneado
  • formato.ts filas de la base → forma de la app

🛡️ Middlewares · middlewares/

Filtros por los que pasa cada request antes de la ruta. Están en autenticar.ts.

  • autenticar token → usuario
  • requerirRol paciente / doctor / admin

🧰 Utilidades · utils/

Lo que usa todo el backend.

  • db.ts Prisma y el registro de auditoría
  • errores.ts ErrorHttp y manejarErrores: todo error → { error }
  • validacion.ts forma de lo que llega (DNI, textos)
  • tiempo.ts “hoy” y “ahora” en hora argentina

🗄️ Base · prisma/

El esquema (schema.prisma), las migraciones con triggers e índices extra, y el seed con los datos de prueba.

  • migrations/ historial de cambios
  • datos/demo.json datos del seed
  • dev.db el archivo SQLite

¿services/ y servicios/ son lo mismo?

No. Se llaman parecido, pero uno está en la app y el otro en el servidor: el de la app pide los datos y el del servidor decide qué se puede hacer y qué se devuelve.

  • Lo llaman las pantallas.
  • Habla con la API, por HTTP, con api().

// services/turnos/turnoService.ts

Las dos puntas se unen en la ruta: GET /api/pacientes/yo/turnos llama a misTurnos(). Las rutas nunca consultan la base: siempre pasan por un servicio (ruta → servicio → Prisma). Y las dos carpetas tienen los mismos temas (sesion/, usuarios/, turnos/, historialMedico/, catalogos/, notificaciones/, admin/): lo que está de un lado se encuentra en la misma carpeta del otro.

¿Qué pasa cuando algo sale mal?

Sí, se evalúan los errores en las dos puntas. El servidor nunca devuelve un error "crudo": siempre un código HTTP y un mensaje en castellano. La app lo convierte en ErrorApi y lo muestra en pantalla.

Código Cuándo Ejemplo de mensaje
400 Datos que no cumplen “Calificá la consulta, de 1 a 5 estrellas.”
401 Sin sesión o vencida “Tu sesión venció. Iniciá sesión de nuevo.”
403 El rol no corresponde “No tenés permiso para esto.”
404 No existe (o no es tuyo) “No existe ese turno.”
409 Choca con algo que ya está “Ese horario ya no está disponible.”
429 Demasiados intentos “Demasiados intentos. Probá de nuevo en unos minutos.”
500 Algo inesperado “Ocurrió un error inesperado…” (el detalle queda en la consola del servidor, no viaja)

En la app: services/apiClient.ts

Todos los pedidos salen de una sola función, pedir(), que usan api() (respuestas JSON) y apiArchivo() (el PDF de un resultado). Ahí se manejan los casos generales para que ninguna pantalla los repita:

1Sin internet, servidor apagado o más de 15 s sin respuesta → “No pudimos conectarnos con el servidor.”
2401 con sesión → borra el token y vuelve al login.
3Cualquier otro error → ErrorApi(status, mensaje); la pantalla muestra el mensaje.
4Falta EXPO_PUBLIC_API_URL en el .env de la app → lo avisa sin intentar el pedido.
5Doble control: la app valida al escribir (más cómodo), el servidor valida siempre (más seguro).

Y la base es la última red: índices únicos y triggers frenan un dato inválido aunque un servicio se equivoque (por ejemplo, dos reservas en el mismo segundo).

Seguridad

Es una app médica: lo sensible nunca se guarda tal cual.

🔐

Contraseñas

Se guardan con scrypt (un hash lento, con sal). Ni el servidor puede leerlas. Login con DNI + contraseña y el mismo mensaje si falla cualquiera de los dos.

🎟️

Sesión con token

Al entrar, el servidor da un token al azar que el celular guarda cifrado (expo-secure-store). En la base queda solo su hash. Vence a los 90 días sin uso. Cómo funciona, paso a paso ↓

📱 x7Fq…9aB→ SHA-256 →🗄️ 3e1c…a04f
🎫

Roles

Cada ruta dice quién puede usarla. Un profesional solo ve a sus pacientes con turno; los PDF, solo el paciente dueño o el médico de la orden.

🪪

DNI escaneado

El registro lee el código del DNI. Se guarda la fecha y un HMAC del número de trámite: nunca la foto ni el código. Un DNI no abre dos cuentas.

🚦

Límite de intentos

5 fallos de login del mismo DNI (o 20 de la misma IP) en 15 minutos → espera.

📝

Auditoría

Login, registro, cambios de contraseña, descargas de resultados y otras acciones importantes quedan en registro_auditoria.

La sesión, paso a paso

Cómo sabe el servidor que sos vos en cada pedido sin pedirte la contraseña cada vez, y cuándo te la vuelve a pedir.

🎟️

Es como la pulsera de un recital. En la entrada mostrás tu DNI y tu entrada (DNI + contraseña) y te ponen una pulsera (el token). Adentro ya no mostrás el DNI: mostrás la pulsera. Si no la usás por mucho tiempo, deja de valer; y si te vas (cerrar sesión), te la cortan.

    ¿Cuándo vence? Probalo

    No vence a los 90 días de haber entrado, sino a los 90 días sin usar la app. Cada vez que la usás, el reloj vuelve a cero. Mové la barra para simular cuántos días pasaron desde la última vez que la abriste.

    Todas las rutas de la API

    Una ruta es una “puerta” del servidor: la app golpea una con un pedido y el servidor responde. El backend tiene 0 puertas, cada una con su archivo en src/rutas/; el mapa con el prefijo de cada archivo está en src/rutas/index.ts. Tocá una para ver qué hace, quién la puede usar, qué le mandás y qué te devuelve.

    ¿Cómo se lee una ruta?

    PATCHEl verbo: qué querés hacer. /apiTodo lo del backend empieza así. /turnosEl recurso: de qué cosa hablás. /:idUn parámetro: cuál de todos (el id va en la URL).
    GET leer POST crear o hacer algo PUT reemplazar una lista entera PATCH cambiar una parte DELETE sacar

    Lo que va después de ? son filtros opcionales (?fecha=2026-11-02). /yo significa “el usuario del token”: el servidor nunca confía en un id de usuario que venga en la URL. Si pedís una ruta que no existe, responde 404 { error: "No existe esa ruta." }.

    Las reglas viven en el servidor

    La app las muestra, pero quien las hace cumplir es el backend. Por ejemplo, la vida de un turno (tocá un estado):

    → → ·

    Todo turno nace pendiente.

    1Solo turnos de tu cobertura: hospitales públicos siempre, privados si aceptan tu plan.
    4Sin doble reserva: un horario tomado no se puede volver a tomar.
    5Cancelar o reprogramar hasta 24 h antes.
    6Feedback solo de un turno cumplido, una vez.
    ⏱Turnos de 30 min dentro de las franjas que carga el profesional.
    🔔Las notificaciones se crean en la misma transacción que el cambio que las dispara; el push sale después. Cuáles hay ↓

    Notificaciones

    Las genera el servidor cuando pasa algo: nadie las crea a mano. Cada una se guarda en la tabla notificaciones (la lista de la campana) y además llega como push al teléfono con Firebase Cloud Messaging (FCM).

    Cómo viaja un aviso

    Cada vez que entrás (al abrir la app con la sesión guardada, con contraseña, con huella o al registrarte), la app pide permiso de notificaciones y manda el token FCM del teléfono (POST /api/notificaciones/fcm-token, desde registrarPushToken()). Queda guardado en esa sesión: al cerrar sesión, el teléfono deja de recibir. En web no se registra.

    Cuando pasa algo, el servicio usa conAviso(): hace el cambio y guarda el aviso (notificar()) en la misma transacción y, recién cuando terminó bien, enviarPush() lo manda sin hacer esperar la respuesta. Si el cambio se revierte, no sale ningún push. Va a cada teléfono del usuario por separado: si uno falla (por ejemplo, un token viejo), los demás lo reciben igual.

    📝 cambio + notificar()→ commit →📲 enviarPush()→ FCM →🔔 teléfono

    Cómo levantarlo

    Desde DocApp Go (backend)/backend. La app apunta a esta API con EXPO_PUBLIC_API_URL en su .env (en el celular, la IP de la computadora).

    # una sola vez: copiar .env.example a .env y completar SECRETO_IDENTIDAD
    # y poner en backend/ el JSON de credenciales de Firebase (sin él no arranca)
    npm install
    npm run db:migrate # crea las tablas
    npm run db:seed   # datos de prueba
    npm run dev       # http://localhost:3000
    curl localhost:3000/api/health # { "ok": true }
